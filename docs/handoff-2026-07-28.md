**Point-in-time record. Not maintained.** Anything about *status* here goes stale
immediately — GitHub Issues is authoritative, always. This file records only what the
issue trail cannot: cross-cutting patterns found during a large batch of work, and the

This repo deleted its hand-maintained progress tracker in #276 precisely because a status

## The pattern worth carrying forward

Across ~28 merged PRs on 2026-07-26/27, nearly every issue filed came from a review
finding that **something asserted did not match what the code did** — not from broken
logic. The code was consistently closer to correct than the prose about it.

Concretely, one false inference — *a failed API query is not a confirmed fact* — was found
and fixed on **five** separate surfaces, because fixing it on one reached none of the
others:

| surface | fixed by |
|---|---|
| check statuses | #226/#233, #235/#250, #236/#244/#251 |
| `Reason` strings | #246/#254 |
| rubric text | #248/#254 |
| `Facts` values | #258/#266/#267, #268/#284 |
| run-history defaults | #287/#289 |

**Why it kept hiding:** only statuses are guarded. `rubricguard` compares a package's
status-assignment code against that package's own rubrics; `assertFixtureChecks` compares
`Status` and reads `Reason` only inside its failure message. **Nothing anywhere asserts on
a `Reason` string, rubric prose, or a `Facts` value** — all of which render verbatim into
signed evidence packs. That gap is still open.

Two structural limits worth knowing before trusting a green run:

- **`rubricguard` cannot see cross-package drift.** A change in `cmd/attestward` invalidated
  rubrics in six collector packages (#263); the guard is structurally blind to it.
- **`threatmodelguard` verifies mention, not membership** (#286). It substring-searches a
  whole bullet, so a job named anywhere in it counts as documented — including inside a
  clause saying something contradictory. Its enumeration is already incomplete and it
  reports green.

## Review lessons that cost real time

- **The least-scrutinised text in any change is the correction itself.** A count, a
  one-word edit, a narrowed claim — nobody re-derives those. It happened repeatedly,
  including in issues filed *about* overclaiming.
- **A claim repeated in N places needs N fixes.** Corrections landed in 2 of 4 sites more
  than once; the sweep is the part that gets skipped.
- **Verify a fix's premise, not just its diff.** Two prescriptions here were structurally
  impossible and were caught only because the implementer proved *why* they could not work
  rather than reporting that they did not.
- **Green output is not a verified outcome.** A `continue-on-error` tick hid a failing
  artifact upload; a `--quiet` push that never landed read as success; a *cancelled* job
  renders identically to a *failed* one in `gh pr checks`. Check state, not summary.
